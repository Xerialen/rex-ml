# SPEC G0.4 — size the movement policy against the tick budget, not against habit

## Why

The per-tick budget is a hard invariant from the original brief: **p99 CPU per game tick < 0.5 ms**
for the full path — DMP integration, MLP forward, tracking guard. The last measurement of that path
was **26.5 µs**, so about **19× of the budget is sitting unused**.

The shipped policy is 14→256→256→8 because that is what the Python side happened to train, not
because it is what the budget allows. Phase 1 is about to spend a lot of compute training a movement
policy; it should train the largest one that fits, and that size should be a measured decision rather
than an inherited default. Growing the network later means retraining from scratch, so this has to be
settled before phase 1 starts, not after.

## What to measure

Per-tick wall cost of the **complete** path (`Automaton::tick`: DMP step + MLP forward + tracking
guard), as a function of architecture. Sweep at least:

- widths 256, 512, 1024, 2048
- depths 2 and 3 hidden layers

Report **p50, p99 and max** in microseconds for each point, with the iteration count used. p99 is
what the invariant is stated in, so a mean is not an answer. Pin the measurement so it is
reproducible: state the thread count, whether the CPU governor or turbo is in play, and run enough
iterations that the p99 is stable across repeats — report the spread across at least 3 repeats of
the whole sweep.

Measure on **this machine**, since that is where the server runs.

## The decision this produces

The largest architecture whose **p99 stays at or under 250 µs** — half the budget, leaving the other
half for everything the tick does besides inference. State the winner explicitly, with its p99 and
its parameter count, and show the point at which the sweep crosses 250 µs and 500 µs so the margin
is visible rather than asserted.

If even 2048×3 stays far under 250 µs, say so and report where the curve actually is — the answer
"the budget does not bind at any size we would plausibly train" is a legitimate and useful outcome,
and more useful than an arbitrary pick.

## Constraints

- Scope: `rtx/crates/rtx-nav/` (the benchmark and any const-generic plumbing needed to instantiate
  other sizes) and a benchmark binary. Do not touch `rtx-game` or anything under `bot/`.
- Never run `cargo fmt` in this tree.
- `cargo test -p rtx-nav` (currently 134 passing) must still pass.
- `Mlp` is const-generic over `NIN`/`NH`/`NOUT`, so the sweep is a matter of instantiating the sizes,
  not of rewriting the type.
- Release build only — a debug-build number is meaningless against this budget.

## What this is not

Do **not** train anything, and do not change the shipped `policy.bin` or its 14/8 input and output
widths. Those are fixed by the contract verified in G0.2. Only the hidden geometry is in question.

## Done when

`evidence/g0.4_budget.json` holds the full sweep (architecture, parameter count, p50/p99/max µs,
iterations, repeats) plus the named winner and the two crossing points. A short table in the report
is enough for the prose.

## Reporting

Numbers with their measurement conditions. If the p99 is unstable across repeats, say so and say by
how much — an unstable p99 against a p99-stated invariant is itself the finding.
