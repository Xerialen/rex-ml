# SPEC G0.3 — wall contact, counted the way the acceptance runner counts it

## Why

The owner's route protocol accepts a run only on **20 consecutive runs with zero wall contacts**.
`rex-env` currently guesses at this with a heuristic:

```rust
let wanted = self.state.vel.length() * TICK_DT;
let blocked = wanted > 1.0 && moved < wanted * 0.5;
```

That flags an ordinary stair riser and a normal landing as wall contacts, and misses a genuine
wall slide that barely slows the hull. So "zero wall contacts" in this environment does not mean
what it means in the acceptance runner, and a policy trained against it would be optimising a
different quantity than the one it is graded on.

**Do not invent a definition.** One already exists, and so does a review of a previous attempt at
it that was **rejected**. Both are in `~/route-lab-src/docs/dm3-incoming-curl-patch-review.md`.
Read it before writing code — it tells you precisely what the last attempt got wrong.

## The definition

Wall contact is the accumulation of **non-floor plane contacts along the selected movement path**.
A surface is floor when its normal satisfies `normal.z >= GROUND_NORMAL_Z` (0.7, already a public
const in `rtx-nav::pmove`). Everything else — walls, ceilings, steep slopes — is non-floor.

"Selected path" is the load-bearing phrase, and it is where the rejected patch failed
(review, "Contact-report correction required for slice A"). `ground_move` traces upward, runs the
upper slide, then traces downward, and the previous patch reported only the upper slide when the
step-up path won — so a ceiling contact in the upward trace or a non-floor contact in the settling
trace was silently dropped. In the other direction, `fly_move` marked some crease/reversal exits as
wall contacts unconditionally, so a floor-only vertical dead stop became a false positive.

Accumulate non-floor contacts from **every trace on the path that actually won**:

- the flat slide, when flat wins;
- the upward trace, the upper slide, **and** the downward settle, when step-up wins;
- the actual accumulated planes on early dead-stop exits, rather than reclassifying those exits
  wholesale.

`start_solid` must **fail closed** — report contact, never silently pass.

## Design constraint that is not negotiable

`pm_step`'s state transition must remain **bit-identical**. The live bot runs this code; a movement
change smuggled in behind a reporting change would invalidate every measurement taken before today.

So: put the work in `pm_step_report`, which returns `(PmReport)` alongside the same mutation, and
make `pm_step` a thin wrapper that calls it and drops the report. Then add an equivalence test —
a deterministic matrix of start states and commands, stepped through both paths, asserting
`origin`, `vel`, `on_ground` and `jump_held` are equal after **every** tick, at both `1/77 s` and
`1/72 s`.

## Scope

- `rtx/crates/rtx-nav/src/pmove.rs` — `PmReport`, `pm_step_report`, `pm_step` as wrapper.
- `rtx/crates/rex-env/src/lib.rs` — use the report; delete the `moved < wanted * 0.5` heuristic.

Do not touch `rtx-game` or anything under `bot/`. Never run `cargo fmt` in this tree.

## Tests you must add

These are the review's own list, which the rejected patch lacked. Numbers 1–8 are required:

1. Equivalence of `pm_step` and `pm_step_report` over a deterministic state/command matrix at both
   tick rates (see above).
2. Clear ground and clear air: `wall_contact = false`, `stepped = false`.
3. Direct wall slide: `wall_contact = true`.
4. Ordinary stair riser, when the step-up path is selected: `stepped = true`,
   `wall_contact = false` for the riser alone.
5. Step-up under a low ceiling: the non-floor contact on the selected path **is** reported.
6. Down-settle onto a steep, non-floor plane: reported.
7. Floor-only vertical landing / dead stop: **no** false wall report.
8. All-solid start: fails closed.

Build them against synthetic hulls where you can — these are semantics tests, not map tests.

## Done when

`cargo test -p rtx-nav` and `cargo test -p rex-env` pass, all eight cases above are covered by name,
and `rex-env`'s reward uses the report rather than the heuristic. `RewardParts::wall` keeps its
meaning (negative on a contact tick); only its source changes.

## Reporting

Report which of the eight cases were straightforward and which forced a judgement call, and say
explicitly whether the state transition is bit-identical or merely close. "Close" is a failure here,
not a nuance.
