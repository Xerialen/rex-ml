# SPEC F1.1 — a trainable environment: real routes, and a batched interface to torch

## Why

`rex-env` steps 139.5 M ticks/s across 64 threads, and the policy trains in torch on an idle H100.
Those two facts only pay off together if the boundary between them is crossed **per batch, not per
step** — a per-step FFI call would throw away three orders of magnitude of throughput.

And the environment cannot yet represent the routes we are graded on. `Route::path` exists, but a
caller with only a start and a goal gets `vec![start, goal]` — a straight line through dm3 geometry,
which is not a route. The policy is a *local waypoint follower* under a planner (that is what the
training distribution says, see `G0.1`), so the planner half has to be real.

`rtx-nav` already has it: `navmesh::query` exposes `find_path`, `find_path_within`,
`find_path_banded` and friends, and `plant_cell` snaps a world position onto the mesh. Use them.
Do not write a pathfinder.

## Part 1 — routes with real paths

- Build the navmesh for a map once, share it read-only across environments, exactly as `Bsp` is
  shared today.
- Add a way to construct a `Route` from two world points: snap both with `plant_cell`, plan with the
  navmesh, and convert the cell sequence into the `Vec<Vec3>` path `Route` already takes.
- A route whose endpoints do not snap, or between which no path exists, must fail **loudly** at
  construction. Silently degrading to a straight line would produce an environment that trains
  confidently on a route that does not exist.
- Keep the existing two-point constructor working; it is what the unit tests use.

## Part 2 — a vectorised, batched interface

Expose `rex-env` to Python via PyO3 with an interface shaped for batching, not for elegance:

- construct **N** environments over a shared map and navmesh, N in the thousands;
- `reset()` → an `(N, 14)` observation array;
- `step(actions)` taking an `(N, 4)` array (`fwd`, `side`, `dyaw`, `jump`) and returning
  observations `(N, 14)`, the five reward terms **separately** as `(N, 5)`, and a done flag `(N,)`;
- environments that finish auto-reset, and the observation returned is the **first observation of
  the new episode**, with the terminal flag telling the trainer what happened. Getting this wrong is
  a classic silent bug: the value bootstrap then crosses an episode boundary.
- step the N environments across the thread pool, since that is where the throughput lives.

Reward terms stay **separate** rather than pre-summed, because the first thing phase 1 must be able
to answer is which term the policy actually responded to. Weighting is the trainer's job.

Zero-copy or near it: hand numpy arrays across, do not build Python lists per step.

## Part 3 — prove the throughput survived

Measure and report **steps/s through the Python boundary** at N = 1024, 4096 and 16384, with a
trivial random policy so the number is the environment plus the boundary and nothing else. Compare
against the 139.5 M steps/s native figure in `evidence/` and state the fraction retained.

If the retained fraction is poor, say so with the number rather than tuning quietly — a slow boundary
is a design finding, and the fix (bigger N, or moving the policy into Rust) is a decision, not a
detail.
